## idle 변환

ShoreRoot(부두/레일/크레인/수면/창고/재고)와 PortalRoot(레일 주행)를 소유 Actor 아래에 둔다. 이동 때 PortalRoot 한 변환으로 정적 부재를 함께 움직인다. 트롤리/훅/와이어는 위치·높이·장구 방향이 바뀔 때만 갱신한다. Idle에서는 RailX가 이미−8이면 재설정하지 않는다. 실제5회 이상 타이머 갱신 동안 API write counter와 USceneComponent.TransformUpdated 이벤트를 함께 관측해0을 확인한다.

## 투영과 DPI

기존 가로 FOV60° 정책을 보존한다. content aspect=(W×SX)/(H×SY), content vertical scale=horizontal×content aspect로 구한 뒤 full target에 X는SX, Y는SY를 적용한다. 따라서 고정 가로 FOV에서 수직식은 대수적으로 이전 식과 같으며, SY만 단독 곱해 화면을 비등방 축소하지 않는다. 코드에서 두 단계를 분리했다. 비영점 lens/frustum 중심도 SX/SY로 스케일 후 영역 중심으로 이동하도록 수정했다. 영역4종/드로어 폭 변화와 DPI1/1.25/1.5/2에서 원의 가로세로 pixel scale 및 역투영·plan picking을 검증한다. 실제 마우스와 자동 수학/Slate 검증은 구분한다.

## 흘수 응답

[선사2024 N-class PDF](https://www.wagenborg.com/media/ozfbgtjf/2024-n-class.pdf)의 ballast6.20m를 **초기 기준 흘수**로 유지한다. [현행 Nassauborg 페이지](https://www.wagenborg.com/fleetlist/n-class/nassauborg)의 TPC SSW는0으로 기재되어 유효한 양의 정수력 값으로 채택하지 않았다. 현행 웹/과거 PDF의 다른 제원 차이를 자동 혼합하지 않는다. 실제 기준 적재상태/TPC 자료가 필요하다.

[출판사 Ship Stability – Notes & Examples, ch1 pp9–10](https://booksite.elsevier.com/samplechapters/9780750648509/9780750648509.PDF)의 수선면/TPC 관계를 사용한다. 단위는 질량t,면적m²,밀도t/m³,TPC t/cm다.

`TPC = ρ × A_wp / 100`, `Δdraft[m] = added_mass[t] / (TPC × 100)`, `loaded_draft = initial_draft + Δdraft`.

실선 TPC 입력이 양수이면 그 값을 쓰고,0이면 합성 `A_wp = 166×22×0.85 = 3104.2m²`, `ρ=1.025`에서 TPC31.81805t/cm를 추정한다.166m/22m는 예제의 등가 길이·폭이고 실제 수선면 길이/폭이 아니다. Cwp0.85는 미확인 표시/해석 가정이다. 인증 체크가 없는 값은 항상 접힌 ‘자료 필요’에 남긴다. 입력/인증 여부·초기 흘수/Cwp/밀도/허용 흘수는 UI와 optional JSON 필드로 보존한다. 구형 계획은 TPC 미확인, 허용 흘수 미제공으로 읽는다.

누적 적재 질량만큼 ShoreRoot를 선박 기준 위로 옮긴다. 이는 선박이 고정 부두/수면에 대해 가라앉는 것과 같은 상대 좌표 표현이며 코일/탱크톱/센서는 선박 좌표에 남는다. 다음 코일 포함 고스트 판정에는 그 질량의 loaded draft로 레일 높이·훅 상/하 양정·접이 커버 통과 높이 여유를 계산한다. 입력 허용 흘수 초과는 위험으로 표시하고 배치는 유지한다.

일정 TPC 선형 모델이다. 실제 흘수별 정수력 곡선, 밸러스트·연료·항만 수위 변화, 종/횡경사에 따른 국부 흘수는 계산하지 않는다. 큰 침하에서 고정 TPC 정확도를 보장하지 않는다. 구조/적재 매뉴얼·현장 수용을 대체하지 않는다.
